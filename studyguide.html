Data Structure #1

Function Pointer Dispatch Table (Route[])

config.h defines the structure. server.c builds and uses it.

What it is

An array of structs, where each struct bundles an HTTP method, a URL path, and a pointer to a function that handles that exact request. Instead of writing a giant chain of if (path == "/api/garden") ... else if (path == "/api/add") ..., the server just walks this array and calls whichever function matches.

Definition — config.h

typedef void (*RouteHandler)(SOCKET fd, const char *body, MYSQL *db);

typedef struct {
    const char   *method;   // "GET" or "POST"
    const char   *path;     // e.g. "/api/garden"
    RouteHandler  handler;  // pointer to the function that handles it
} Route;
Key idea: RouteHandler is a type that can hold the address of any function matching void f(SOCKET, const char*, MYSQL*). Every api_* function in db.c and ai.c matches this exact signature, so all of them can be stored in a Route.

Construction — server.c

static Route routes[] = {
    { "GET",  "/",                     serve_html       },

    { "POST", "/api/garden/water",     api_water        },
    { "POST", "/api/garden/remove",    api_remove       },
    { "POST", "/api/garden/bulk-water",api_bulk_water   },
    { "POST", "/api/garden/fav",       api_toggle_fav   },
    { "POST", "/api/auth/login",       api_login        },
    { "POST", "/api/auth/register",    api_register     },
    { "GET",  "/api/water-history",    api_water_history},
    { "GET",  "/api/stats",            api_stats        },
    { "POST", "/api/notes/add",        api_add_note     },
    { "GET",  "/api/notes",            api_get_notes    },

};
#define NUM_ROUTES (sizeof(routes) / sizeof(routes[0]) - 1)

18 real entries, terminated with a {NULL, NULL, NULL} sentinel — this is how the code knows where the array ends, since plain C arrays don't track their own length at runtime.

Lookup algorithm — server.c

static RouteHandler find_route(const char *method, const char *path) {
    char base[256];
    strncpy(base, path, sizeof(base) - 1);
    base[sizeof(base) - 1] = '\0';
    char *q = strchr(base, '?');
    if (q) *q = '\0';                 // strip off ?query=string

    for (int i = 0; routes[i].method != NULL; i++) {
        if (strcmp(method, routes[i].method) == 0 &&
            strcmp(base, routes[i].path) == 0) {
            return routes[i].handler;  // found it — return the function pointer
        }
    }
    return NULL;   // 404
}
Request arrives
→
parse method + path
→
strip ?query
→
linear scan routes[]
→
match? call handler() : send 404

Where it gets called — server.c → handle_client()

RouteHandler handler = find_route(method, path);
if (handler) {
    EnterCriticalSection(&g_db_lock);
    if (strcmp(method, "GET") == 0) handler(cfd, req, g_db);
    else                            handler(cfd, body, g_db);
    LeaveCriticalSection(&g_db_lock);
} else {
    send_resp(cfd, "404 Not Found", "application/json", "{\"error\":\"Route not found\"}");
}

Once the right function pointer is found, it's simply called like a normal function — handler(cfd, body, g_db) — even though at compile time nobody knows exactly which function this will be. That decision happens at runtime.

Complexity & honest analysis

Operation Complexity Why
Route lookup O(n) Linear scan through all 18 routes worst case
Route dispatch (once found) O(1) Direct function pointer call
Could be optimized to a hash map (path → handler) for O(1) lookup, but with only 18 routes, linear scan is effectively instant — this is a great honest point to make if your teacher asks "can this be improved?"
Data Structure #2

Realloc-Doubling Dynamic Buffer

db.c — used inside api_plants(), api_garden(), and similar JSON-building handlers.

What it is

A manually-built growable array (the same technique std::vector or Java's ArrayList use internally) that starts at a fixed size and doubles its capacity whenever it's about to overflow — instead of crashing or truncating data. Used to build a JSON response string when you don't know in advance how many database rows (plants, garden entries) there will be.

Full pattern — db.c → api_plants()

int cap = 65536, len = 0;                 // start with a 64KB buffer
char *buf = (char *)malloc(cap);
buf[len++] = '[';                          // begin JSON array

MYSQL_ROW row;
int first = 1;
while ((row = mysql_fetch_row(res))) {

    // ... build one JSON object for this row into item[] ...
    char item[4096];
    int n = snprintf(item, sizeof(item), "%s{...plant fields...}",
                      first ? "" : ",", ...);
    first = 0;

    // GROW the buffer if this item won't fit
    while (len + n + 2 >= cap) {
        cap *= 2;                                   // double capacity
        char *tmp = (char *)realloc(buf, cap);       // reallocate
        if (!tmp) { free(buf); /* handle OOM */ }
        buf = tmp;
    }

    memcpy(buf + len, item, n);            // copy item into the big buffer
    len += n;
}
buf[len++] = ']';
buf[len] = '\0';
send_resp(fd, "200 OK", "application/json", buf);
free(buf);

Step-by-step visual

Initial: cap=65536 len=0 buf = [ ...................... ] (empty) Add item 1: len grows → buf = [ {plant1} .................... ] Add item 2: len grows → buf = [ {plant1},{plant2} ............ ] ... Buffer full? len + next_item + 2 >= cap → TRUE → cap *= 2 (e.g. 65536 → 131072) → realloc(buf, cap) (old data preserved automatically by realloc) → keep appending into the now-bigger buffer

Why realloc instead of just guessing a big size?

121 plants with long descriptions could need more than 64KB of JSON. Rather than hardcoding a giant fixed buffer (wasteful for small responses) or risking overflow (dangerous), the buffer starts small and grows only when needed, doubling each time. This gives amortized O(1) append cost — most appends are cheap (just memcpy), and the occasional expensive realloc happens rarely enough that the average cost per append stays constant.

Complexity & honest analysis

Operation Complexity Why
Append one JSON item (no resize) O(k) memcpy of k bytes
Append one JSON item (triggers resize) O(n) realloc copies all n existing bytes
Overall, across all appends Amortized O(1) Resizes become rare as capacity grows exponentially
